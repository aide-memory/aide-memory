Here's how it works in a nutshell:

Auto memory is essentially Claude Code taking its own notes as it works with you. Claude saves things like build commands, debugging insights, architecture notes, code style preferences, and workflow habits. It doesn't save something every session — it decides what's worth remembering based on whether the information would be useful in a future conversation. 
Claude

Where it lives: Each project gets its own memory directory at ~/.claude/projects/<project>/memory/. The directory contains a MEMORY.md entrypoint and optional topic files. 
Claude
 So if Claude notices you always use pnpm instead of npm, or that a particular test requires a local Redis instance, it writes that down.

How it loads: The first 200 lines of MEMORY.md are loaded at the start of every conversation. Claude keeps it concise by moving detailed notes into separate topic files (like debugging.md or patterns.md), which are read on demand when needed. 
Claude

The key distinction is between two things:

CLAUDE.md — your instructions to Claude (coding standards, architecture rules, etc.)
MEMORY.md — Claude's own notebook about your project
Auto memory is on by default. You can toggle it via /memory in a session, or disable it with the environment variable CLAUDE_CODE_DISABLE_AUTO_MEMORY=1. 
Claude

You can also explicitly tell it to remember things by saying something like "remember that we use pnpm, not npm" or "save to memory that the API tests require a local Redis instance" — and it writes those immediately.

Auto memory is machine-local. All worktrees and subdirectories within the same git repository share one auto memory directory, but files are not shared across machines or cloud environments. 
Claude

There's also a separate Session Memory feature that automatically captures what you did during a session — which files you edited, decisions made, where you left off — and loads relevant summaries when you start a new session. 
Claude Fast

So between CLAUDE.md, auto memory, and session memory, Claude Code builds up a pretty rich per-project context over time — it just doesn't connect to our conversations here on claude.ai.

This is the right question. What's the defensible moat even if Anthropic (or Cursor, or GitHub) ships native memory?

The Things They Can't Easily Replicate
1. Tool-agnosticism — being the neutral layer

This is the single biggest one. Anthropic will never build great memory for Cursor users. Cursor will never build great memory for Claude Code users. GitHub Copilot will never optimize for Windsurf users. Each company is incentivized to lock you into their ecosystem.

A developer who uses Claude Code for big features, Cursor for quick edits, and Copilot through GitHub PRs — that person needs a memory layer that none of those companies are motivated to build. Even if Anthropic ships perfect memory for Claude Code, it won't help when that developer opens Cursor.

And the trend is toward using more tools, not fewer. People are combining tools strategically based on what each does best.

2. Memory portability — you own your graph, not the vendor

Right now if you invest heavily in Claude Code's MEMORY.md and CLAUDE.md files and then switch to a different tool, or Anthropic changes their approach, all that accumulated context is trapped in Anthropic's format. Same with Cursor's .cursorrules.

A tool that says "your memory is yours, it's an open format, export it anywhere, take it with you" — that's a proposition no platform vendor will ever offer because it's against their interests. They want your context locked in.

This is similar to how 1Password succeeded despite every browser having built-in password management. The value is in being the neutral, portable layer the user controls.

3. The reasoning layer — not just what but why

This came up earlier. Every native memory system stores flat facts. "Uses pnpm." "Port 3001." A tool that captures decision graphs — "switched from npm to pnpm because monorepo builds were slow, specifically the payments service, after trying yarn first and hitting peer dependency issues on Feb 3" — that's fundamentally different from what any current tool offers.

This matters because when you're debugging something six weeks later, knowing the reasoning chain behind past decisions is vastly more useful than knowing the final choice. No native auto-memory captures this because it would require structured extraction that goes far beyond noting preferences.

4. Cross-project intelligence

Native memory systems are project-scoped. Claude Code's auto-memory lives in ~/.claude/projects/<project>/. Cursor's context is workspace-scoped. Neither knows that your API project and your frontend project are related, or that a schema change in one should inform work in the other.

A memory layer that understands your portfolio of projects — how they connect, share dependencies, affect each other — is something a single-tool vendor has no reason to build because they don't see cross-project workflows as their problem.

5. Team memory that's actually useful

This is a huge untapped space. When a new developer joins a team, they spend weeks absorbing unwritten context — why was this architected this way, what did we try that didn't work, what are the unspoken conventions. That knowledge lives in people's heads and scattered Slack threads.

A tool that accumulates team-level project memory — not just individual preferences but shared architectural decisions, past mistakes, institutional knowledge — and makes it available to any team member's coding agent regardless of which tool they use. That's genuinely hard for any single platform to build because it requires being embedded across everyone's different tool choices.

6. Temporal intelligence — understanding change over time

Zep does this for enterprise chat apps, but nobody does it well for coding. Your codebase evolves. Decisions that were right three months ago are wrong now. Dependencies update. APIs change.

A memory system that tracks when things were true, knows when facts become stale, and can say "you decided X six weeks ago but since then Y changed, so you might want to reconsider" — that's a qualitative leap beyond anything current. The embedding model is what turns text into numbers so the memory system can search for relevant memories.

When you store a memory like "switched from npm to pnpm because of monorepo build speed," the system needs to convert that sentence into a mathematical representation (a vector) so that later, when you're working on something related to build tooling, it can find that memory by similarity rather than exact keyword match.

That's what an embedding model does — it converts text into vectors, and similar concepts end up close together in vector space. So "build is slow" would be close to "monorepo performance issue" even though they share no words.

Why OpenMemory needs an OpenAI API key: Under the hood, it uses OpenAI's embedding model (like text-embedding-3-small) to create these vectors. Every time you store or search a memory, it sends that text to OpenAI's API, gets back a vector, and stores/searches it in Qdrant (their vector database).

Why that undermines the "local-first" pitch: OpenMemory says your data stays on your machine. And it does — the vector database is local. But every piece of text you store still gets sent to OpenAI for embedding. So your code context, architectural decisions, project details — all of that hits OpenAI's servers. For privacy-conscious developers or regulated industries, that's a dealbreaker.

What a local embedding model means: Instead of calling OpenAI, you run a model locally on your machine that does the same conversion. Models like nomic-embed-text, all-MiniLM-L6-v2, or mxbai-embed-large can run via Ollama or directly in Python. They're smaller, free, and nothing leaves your machine.

The tradeoff is that local models are slightly less accurate than OpenAI's best embedding models, though for code-related memory (where the vocabulary is relatively constrained and patterns are consistent), the gap is small enough to not matter much in practice.

So when I mentioned it as a differentiator — a memory tool that's genuinely local, not "local storage but cloud embeddings" — that's what I meant. No API keys, no data leaving the machine, no per-operation costs. True local-first.

Great question. This gets into the actual architecture of how you'd build this thing.

SQLite vs Vector Search — It's Not Either/Or
You actually want both, and here's why they solve different retrieval problems.

What SQLite is good at:

Exact, structured lookups. "Show me all memories tagged as architectural decisions for the payments service from the last 30 days." That's a SQL query — fast, precise, predictable. You know exactly what you're filtering on.

SQLite is also great for the metadata layer — timestamps, project associations, tags, relationships between memories, which tool created them, when they were last accessed. All of that is relational data that belongs in a structured database.

And SQLite is a single file, zero config, ships everywhere. Perfect for a local-first tool.

What vector search is good at:

Fuzzy, semantic lookups. You're working on authentication and the system needs to find that memory from three weeks ago where you discussed JWT token expiration — but that memory was tagged under "API security" and mentioned "session management," not "authentication." A SQL LIKE query won't find it. Vector similarity will, because the embeddings are semantically close.

This is the core use case for memory retrieval — you rarely know exactly what you're looking for. You need "things related to what I'm currently doing."

The practical architecture:

SQLite
├── memories table (id, text, project, tool_source, created_at, updated_at, tags, type)
├── relationships table (memory_id_a, memory_id_b, relationship_type)
├── access_log table (memory_id, tool, timestamp)
└── vectors table (memory_id, embedding BLOB)
You store the vectors right inside SQLite. You don't need Qdrant or Pinecone or any separate vector database. sqlite-vec is an extension that adds vector similarity search directly to SQLite. One file, no infrastructure, and you get both structured queries and semantic search.

Your retrieval then becomes a hybrid:

Pre-filter with SQL — narrow to the current project, recent memories, relevant types
Rank with vector similarity — among those filtered results, find the most semantically relevant to the current task
Post-filter with recency/access weighting — boost recent memories, decay stale ones
This is significantly better than either approach alone. Pure vector search returns semantically similar stuff that might be from the wrong project or completely outdated. Pure SQL search misses anything not tagged perfectly.

On "create vectors raw":

If you mean manually computing and storing vectors without an embedding model — that's not really possible. You need something to turn text into vectors. The question is where that runs.

But if you mean storing raw embedding floats in a SQLite BLOB column rather than using a dedicated vector DB — yes, absolutely. With sqlite-vec you get:

sql
-- Store
INSERT INTO memories (text, embedding) VALUES ('switched to pnpm for monorepo speed', ?);

-- Search
SELECT text, vec_distance_cosine(embedding, ?) as distance
FROM memories
WHERE project = 'aide'
AND created_at > '2026-01-01'
ORDER BY distance
LIMIT 5;
One file. No Docker. No Postgres. No Qdrant. No OpenAI API key if you use a local embedding model. Copy it to another machine and everything works.

That's genuinely local-first — and it's a real differentiator over OpenMemory's stack of Docker + Postgres + Qdrant + OpenAI.

The tradeoff:

sqlite-vec does brute-force search, not approximate nearest neighbor. For a personal memory store (thousands to low tens of thousands of memories), that's fine — search is still milliseconds. It breaks down at millions of records, but no individual developer is storing millions of memories.

For a team/enterprise version with much larger datasets, you'd eventually need to graduate to something like Qdrant or pgvector. But for the core product, SQLite + local embeddings is the simplest architecture that actually works and the honest local-first story.

The Retrieval Hierarchy
Level 1: Direct match (cheapest, fastest, most precise)

The agent is working in a file. You know the file path, the project, the function name, the module. That's enough to do a direct SQL lookup:

sql
SELECT * FROM memories
WHERE project = 'aide'
AND (tags LIKE '%auth%' OR file_path LIKE '%auth/%')
AND type IN ('decision', 'bug_fix', 'architecture')
ORDER BY updated_at DESC
LIMIT 10;
```

No embeddings needed. The context you already have — file path, module name, project — is a strong enough signal to pull relevant memories. This should be the first thing the system tries, every time.

**Level 2: Graph traversal (still cheap, adds relationships)**

The direct match found a memory: "chose JWT for auth tokens." The graph knows that memory is linked to another memory: "JWT refresh flow needs Redis for token blacklisting," which links to "Redis connection pooling configured for 10 connections." Follow the edges. You get a chain of related decisions without any semantic search.

This is where SQLite's relational strength shines. Foreign keys and joins are fast and deterministic.

**Level 3: Semantic search (expensive, but catches what the others miss)**

Direct match found nothing. Graph traversal hit a dead end. The developer is working on something that doesn't have obvious keyword overlap with existing memories. Now you embed the current context and do a similarity search.

But crucially — you're searching a *pre-filtered* set, not the entire memory store. You've already narrowed by project, by recency, maybe by type. The vector search is running over hundreds of candidates, not thousands.

## What the Model Should Be Prompted to Do

This is the key design question. The agent (Claude, Cursor's model, whatever) needs to know *how* to use the memory system. You'd expose MCP tools that make the hierarchy explicit:
```
Tool 1: lookup_memory(project, file_path?, tags?, type?)
  → Direct SQL match. Agent should try this FIRST.

Tool 2: related_memories(memory_id)
  → Graph traversal from a known memory.
  
Tool 3: search_memory(query, project?)
  → Semantic search. Agent uses this when lookup returns nothing useful.
  
Tool 4: store_memory(text, type, tags?, related_to?)
  → Save with structured metadata + auto-embed.
```

Then in the MCP tool descriptions, you're explicit about ordering:
```
lookup_memory: Use FIRST. Query memories by known attributes
like project, file path, tags, or type. Fast and precise.
Only fall back to search_memory if this returns insufficient results.

search_memory: Use when lookup_memory returns nothing relevant
or when the connection between current work and past context
isn't obvious from metadata alone. Slower but finds
semantic relationships.
```

The model follows tool descriptions. If you tell it to try the cheap thing first, it will. This is how you keep token injection minimal too — the direct lookup returns exactly what matches, not a cloud of "maybe related" results.

## The Store Side Matters Too

The retrieval hierarchy only works if memories are stored with good metadata in the first place. When the agent saves a memory, the prompt should guide it to include:

- **What** — the fact or decision
- **Why** — the reasoning
- **Where** — which files, modules, services are involved
- **Type** — decision, bug_fix, preference, architecture, convention, todo
- **Relations** — links to existing memories this connects to

If storage is sloppy (just dumping raw text with no metadata like current auto-memory does), then you're forced to lean on semantic search for everything, which is slower, less precise, and more token-hungry.

So the storage prompt matters as much as retrieval:
```
store_memory: Save a structured memory. Always include:
- type: one of [decision, bug_fix, preference, architecture, convention, todo]
- tags: relevant modules, services, or concepts
- related_to: IDs of existing memories this connects to (use lookup_memory to find them)
- reasoning: why this decision was made, not just what was decided
The Compounding Effect
What makes this powerful over time is that levels 1 and 2 get better as the memory store grows. More memories means more direct hits, more graph connections, less reliance on fuzzy semantic search. The system naturally shifts toward cheaper, more precise retrieval as it accumulates context.

That's the opposite of current auto-memory systems, which just pile up flat text and make retrieval harder over time because there's more noise to search through.

So to directly answer your question — yes, semantic search should be the fallback, not the default. Structure the data well on the way in, and most retrieval can be deterministic. The embedding model is your safety net for when the structured path doesn't have coverage, not your primary retrieval mechanism.

How the Connection Works in Practice
When the agent is working in packages/payments/ and needs context:

Direct lookup hits: file_context matches, project matches, tags match "payments-service." Returns the memory immediately. The embedding was never touched.

But now imagine the agent is working in packages/checkout/ on a build issue. There's no memory with file_context matching checkout. No tag for "checkout." The direct lookup returns nothing.

The semantic search takes the agent's current context — "checkout build is failing with dependency resolution errors" — embeds that text into a vector, then compares it against all stored memory vectors. The pnpm memory scores high because "dependency resolution errors" is semantically close to "peer dependency resolution bugs" and "builds timing out." The embedding bridges the vocabulary gap that structured search can't.

Why Semantic as Fallback, Not Default
Three concrete reasons:

1. Precision

Semantic search returns similar things, not exact things. If you have 500 memories and search for "authentication," you'll get back auth-related memories — but also maybe memories about "authorization," "session management," "user onboarding," and "security headers." They're all semantically close. You have to inject all of them into the agent's context and hope it figures out which are actually relevant.

A direct lookup for tags LIKE '%auth%' returns exactly the auth memories. No noise.

When the agent is spending tokens on context, precision matters. Every irrelevant memory injected is tokens wasted and potential confusion added.

2. Determinism

SQL queries return the same results every time. You can debug them, predict them, log them. If a memory isn't being found, you check the tags and fix them.

Embedding similarity is probabilistic. Small changes in phrasing change which memories surface. The distance threshold you pick (how "similar" is similar enough?) is a tuning parameter that affects everything. Two semantically identical sentences might produce slightly different vectors depending on the model. It's harder to debug why a memory wasn't found.

For something that's feeding context to an agent that's writing code, you want predictability.

3. Cost

Every semantic search requires embedding the query — that's an inference call, either to an API or a local model. Then computing cosine distance against potentially thousands of vectors. Even with sqlite-vec, it's scanning every vector in the filtered set.

A SQL index lookup is nearly free by comparison. If 80% of retrievals can be handled by direct match (because good metadata was stored), you're saving significant compute on every interaction.

When Semantic Search Is Essential
That said — there are cases where only semantic works:

The developer is working on something genuinely novel with no matching tags or file paths
The connection between current work and past memory is conceptual, not structural ("this performance issue reminds me of that caching problem we solved")
The vocabulary has drifted — what the team called "the gateway service" six months ago is now called "the API layer"
These are real situations and they happen often enough that you can't skip semantic search entirely. That's why it's the fallback — it catches what structured search misses.

The Real Answer
You could do semantic-first and it would work. The system wouldn't break. It would just be slightly less precise, slightly less predictable, and slightly more expensive on every query. For a small memory store, the difference is negligible.

The reason to architect it as a hierarchy is that it scales better. As the memory store grows to thousands of entries across multiple projects, the noise problem in pure semantic search compounds. Direct match stays just as precise at 10,000 memories as it was at 100. Semantic search gets noisier because there are more near-matches competing for attention.

So it's a design choice about where you want the system to be in a year, not just today.

Option 1: Agent Calls On Demand (Tool-Based)
You register aide as an MCP server. The agent (Claude Code, Cursor's model, whatever) sees the available tools in its context and decides when to call them.

How it works:

The MCP tool descriptions tell the agent the tools exist:

store_memory: Save important context from this session.
lookup_memory: Find memories by project, tags, or file path. Try this FIRST.
search_memory: Semantic search when lookup returns nothing relevant.
The agent reads these descriptions at session start and makes its own judgment calls about when to use them. You're relying on the model being smart enough to think "I should check memory before starting this task" and "I should save this decision before moving on."

Pros:

Simple architecture — you're just an MCP server, no hooks needed
Works with any MCP-compatible tool without custom integration
The agent has full context about what it's doing and can make intelligent decisions about what to store and retrieve
No wasted token injection — only retrieves when the agent thinks it's relevant
Cons:

The agent might forget to call it. Models don't always use available tools unless prompted. You might work through an entire session and the agent never checks memory because it didn't think to.
Retrieval quality depends on the agent's judgment about when to search, not just what to search for
Different models have different tendencies — Claude might use tools proactively, Cursor's model might not
You're at the mercy of each tool's MCP implementation and how prominently they surface available tools

A hook or middleware fires at session start (or on specific events like opening a file), queries the memory store, and injects relevant memories directly into the agent's context before it even starts working.

Queries the aide memory store for relevant context
Injects the results into the agent's system prompt or initial context
The agent doesn't decide whether to check memory — it just has the relevant memories already in its context window, like how CLAUDE.md is already loaded at session start.

If you give it two tools — lookup_memory and search_memory — you're asking it to decide which retrieval strategy is appropriate before it even knows what's in the memory store. That's a decision the agent isn't equipped to make well. It doesn't know how your memories are tagged, what metadata exists, or whether a direct match is likely to succeed. It'll either always pick one (probably semantic because it feels safer), or waste a tool call trying direct first and then calling semantic as a follow-up, burning tokens and latency on two round trips.

One tool. One call. You handle the strategy internally.

retrieve_memory(query, project?, context?)
The agent says what it needs. Your engine decides how to find it.

Under the hood:

Parse the query for structured signals — does it contain a file path, a module name, a known tag, a specific technology? If yes, run a direct SQL lookup using those as filters.
If direct returns results above a confidence threshold — done. Return them. The agent never knows or cares that semantic search exists.
If direct returns nothing or results are below threshold — run semantic search over the pre-filtered set (same project, recent time window). Return the best matches.
If both return nothing — say so honestly. "No relevant memories found." Don't hallucinate or stretch.
The agent gets back results in the same format regardless of which path found them. It doesn't need to know. It asked a question, it got an answer.

Why this matters:

Every tool call the agent makes costs tokens — the call itself, the response, and the model reasoning about what to do with the result. Two separate tools means the model sometimes calls both "just to be thorough," doubling the cost for the same information. Or it picks the wrong one and gets bad results on the first try.

A single interface also means you can change the retrieval strategy anytime without touching the tool interface. You could add graph traversal as a middle step between direct and semantic tomorrow. You could add a re-ranking layer. You could add caching for recently accessed memories. None of that changes what the agent sees — it's still one tool, one call, one response.

The one exception:

Store should be separate from retrieve. Don't combine storage and retrieval into one tool. The agent's intent when storing ("save this for later") is fundamentally different from retrieving ("what do I need to know"), and combining them creates ambiguity in the tool description that makes models use it worse.

So the final interface is:

retrieve_memory(query, project?, context?)
  → handles direct, graph, semantic internally
  → returns ranked results with source metadata

store_memory(text, type, tags?, reasoning?, related_to?)
  → structured storage with metadata
  → returns confirmation
Two tools. Clean separation. The intelligence lives in your retrieval engine, not in the model's tool selection.
